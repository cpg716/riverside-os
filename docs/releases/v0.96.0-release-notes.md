- Status: **Same-version updater rebuild. Local Playwright was explicitly
  waived for this rerun; publication still requires exact-commit GitHub

## Release summary

v0.96.0 turns the recent Wedding Collect & Build work into a clearer,
restart-safe production workflow. Staff can prepare exact items for every party
member, review funding and attribution, then create the separate member-owned
Transactions and Wedding Fulfillment Orders in one guided action through the
existing audited checkout path. The release also makes product variation
selection easier to navigate and aligns Main Hub audit/repair scripts with the
real production installation contract. ROSIE now ships as a fully certified
local Gemma 4 stack, and staff workflows consistently support keyboard, mouse,
touch, and assistive input.

## Wedding deposits and member order building

- **Collect & Build** prepares party parent products, exact member variations,
  optional alterations, individual No Tax reasons, and apply-all or per-member
  salesperson attribution as reloadable drafts.
- Approved payer funding unlocks **Create All Member Transactions**. Each
  beneficiary receives a separate financial Transaction and Wedding
  Fulfillment Order through the normal server-validated atomic checkout path.
- Stable checkout identities make partial retry safe: completed members remain
  posted once and a retry resumes only unfinished members.
- Deposit entry supports one per-member amount applied only to selected party
  members, with individual overrides still available.
- Deposit Only activity can be resumed from the original payer's **Orders &
  Receipts** history, which reloads member allocations, exact held balances,
  posted Transactions, and receipt links.
- Selecting a wedding member directly in Register can open the same parent-item
  and exact-variation builder while identifying available held funds and the
  contributing payer.
- Builder navigation, draft editing, and item selection remain nonfinancial.
  Writes happen only through the existing audited checkout service.
- Completion presents member totals and individual printable receipts.

## Wedding lifecycle, scheduling, and tracking archive

- Ordered, Received, Ready for Pickup, and Picked Up are derived from the
  authoritative non-takeaway Transaction/Fulfillment Order line lifecycle.
  The Wedding grid no longer creates a parallel fulfillment state.
- Pickup appointments can be marked attended, but merchandise pickup must be
  completed through Orders/Register so inventory, tender, fulfillment,
  alterations, shipping, and receipt links stay intact.
- Linked Measurement/Fitting attendance and the matching member milestone are
  one atomic write. Appointment conflict overrides retain the exact ROS staff
  assignment, Manager Access identity, validation message, and written reason.
- Party/member mutations use authenticated ROS staff attribution, and their
  activity entries commit with the business update.
- Recent member financial activity can open its exact Transaction in Orders,
  where the linked fulfillment, alteration, shipment, payment, and receipt
  evidence remains available.
- Passed or historically incomplete wedding tracking can be archived without completing
  a fictional ROS workflow. The read-only archive review discloses Transactions, open
  balances, held deposits, fulfillment lines, appointments, and alterations;
  unresolved work requires explicit acknowledgment and remains unchanged.

## Validation and publication contract

Release publication requires all of the following on one exact commit:

- version parity across root, client, server, Tauri, ROS Dev Center, Deployment
  Manager, Server Manager, CounterSync Bridge, locks, and Windows metadata;
- generated Help and ROSIE knowledge-drift checks;
- Rust formatting, clippy/checks, unit/integration tests, client lint,
  typecheck, production builds, and the non-E2E local release gates;
- local Playwright is explicitly waived for this same-version rebuild at the
  operator's direction; it is not represented as local runtime proof;
- exact-commit GitHub Lint and Playwright gates;
- successful non-publishing Windows and macOS candidates;
- an annotated `v0.96.0` tag on the candidate commit;
- candidate promotion with artifact provenance verification;
- one current Windows deployment ZIP plus five matching updater/build-manifest
  pairs, all resolving to the release commit;
- a public, non-prerelease GitHub release marked Latest.

## Operational boundary

Source, CI, tag, GitHub release, packaged assets, deployment, and live runtime
are separate claims. GitHub publication does not prove installation. Store
signoff still requires the physical Main Hub and Register estate to report
v0.96.0 and the exact build SHA, pass `/api/ready` and `/api/health`, show the
expected migration ledger, and complete printer, payment-terminal, backup, and
representative Wedding Builder smoke checks.
