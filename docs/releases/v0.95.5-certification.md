## Operational boundary

Passing source and GitHub publication gates does not prove that a production
Main Hub installed the build. Production signoff still requires the installed
version and SHA, `/api/ready`, database-backed lookup, workers/dependencies, and
`/api/health`, followed by Register, printer, payment-terminal, backup, and
store-workflow checks on the physical environment.

Payment production signoff additionally requires four observed workflows on
the exact installed build: one Card Reader approval, one Card Not Present
approval, one canceled Card Not Present attempt, and a clean following sale.
Each approval must appear once in the ROS payment ledger with the same amount
and provider transaction reference; the canceled attempt must create no tender;
and the following sale must open without inheriting a routing or checkout lock.

For this rebuild, operational continuity starts from a Main Hub already
directly updated through `55eb791f`. That runtime reported healthy and ready,
had migrations 163 and 164 applied, showed TXN-624427 cancelled/refunded with
`$0.00` balance due and a printable refund receipt, and had zero closed,
fully-refunded obligations with a nonzero customer balance. The replacement
tag and assets must descend from that SHA so the normal updater recognizes the
existing migration ledger and advances it without replaying or rewriting
applied migration bytes.
