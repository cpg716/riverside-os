  the GitHub release after asset publication; production installation and
  physical signoff remain separate.**

## Rebuild changes

- **Park Sale now preserves the complete Wedding Collect & Build workflow.**
  The server-backed parked payload includes every saved member draft, its exact
  product variants, fulfillment choices, salesperson attribution, payer Cart,
  deposit allocations, current member, and current workflow step. Recall
  restores that complete nonfinancial work instead of retaining only the payer
  Cart and deposits.
- The Wedding Deposit salesperson is restored independently from payer
  merchandise attribution, and clearing a sale removes both values before the
  next customer. This prevents a recalled workflow from failing payment because
  its already-confirmed deposit salesperson became an empty hidden field.
- Receipt Builder previews now expose the complete customer-facing receipt
  structure and configurable placement tokens, giving staff a truthful preview
  before saving a layout.
- Source-locked migration 176 supersedes five reviewed Counterpoint
  open-document shells that duplicated ordered-item subsets from sales already
  booked in ROS. It retains the original ROS Transactions, provider-backed
  payments, inventory, fulfillment, and financial evidence; removes only the
  copied non-provider allocations; and records immutable reconciliation and
  operator audit evidence.
- Local Playwright E2E is intentionally skipped at operator direction.
  Exact-commit GitHub Playwright remains a blocking publication gate alongside
  Lint, Windows packaging, macOS packaging, and updater-manifest verification.

## Helcim terminal dispatch and non-blocking payment review

- Current Register clients now identify their exact source build before Card
  Reader, Card Not Present, or Saved Card dispatch. A known Register/Main Hub
  mismatch stops before Helcim receives a request and reports both build
  prefixes, preventing a card approval from being stranded between incompatible
  checkout contracts.
- Repeated Card Reader requests for the same open checkout now return the
  existing pending attempt instead of dispatching a second terminal purchase.
  A genuinely new checkout can still replace the earlier ROS routing
  reservation while retaining all prior provider evidence for reconciliation.
- Live terminal purchases now send the amount directly to the selected Helcim
  reader. ROS no longer runs the Settings diagnostic ping immediately before a
  purchase because that separate reader interaction could leave the terminal
  displaying **Device Connected** without receiving the amount due.
- A prior pending, failed, timed-out, expired, or unresolved Helcim attempt is
  retained in Payments Health with its Register, checkout, provider evidence,
  and recovery history, but it no longer owns a terminal-routing reservation
  against the next payment.
- The Tauri checkout no longer turns historical or unresolved payment evidence
  into a Register-wide tender lock. Restore remains available to refresh,
  reconcile, or attach a verified result; cash, check, gift card, store credit,
  and other permitted tenders remain usable while review evidence is retained.
- A confirmed Helcim approval for the exact same checkout remains protected
  from a duplicate charge. ROS requires that real money to be attached through
  the original checkout recovery path rather than treating it like a stale
  reservation or moving it to another customer.
- The production Main Hub was advanced to the server-side routing fix during
  the incident and reported ready with PostgreSQL connected. The Tauri client
  behavior is delivered by this rebuilt updater; production installation of
  that desktop package remains a separate operator action.
- Focused Helcim dispatch and routing-reservation tests passed with Rust
  formatting/checks, TypeScript typecheck, client lint, Help impact, and
  whitespace validation. Local Playwright E2E is intentionally skipped at
  operator direction; exact-commit GitHub Playwright remains a publication
  gate.

## Checkout attribution, exchange commissions, recovery, and pickup receipts

- Every new merchandise or service line must have either the checkout's
  primary salesperson or its own line salesperson before Payment opens or any
  tender begins. A salesperson retained on an existing pickup line cannot
  satisfy a newly added alteration fee or merchandise line.
- Exchanges preserve the original and replacement salesperson through the
  client handoff, checkout request, recovery payload, commission ledger, and
  audit evidence. Recovery rejects a changed salesperson identity instead of
  silently reallocating commission.
- A blocked Checkout Recovery resolves automatically only when Riverside
  verifies the exact committed Transaction Record and the sole request
  difference is completed primary salesperson attribution. Differences in
  payment, merchandise, totals, tax, customer, Register session, or other
  checkout identity remain blocked for audited review.
- Merchandise linked from an existing Order always prints under **PICKED UP**,
  including when the checkout also adds a fee or new merchandise. **Taken
  Today** remains reserved for merchandise first sold and taken home in the
  current checkout.
- Focused attribution, exchange, commission, recovery-integrity, and receipt
  tests passed with Rust formatting, TypeScript, lint, Help generation, Help
  impact, and whitespace checks. Local Playwright E2E is intentionally skipped
  at operator direction; exact-commit GitHub Playwright remains the publication
  gate.

## Register workflow and presentation

- **Update Item** in Customer Orders now opens its variation drawer above the
  Order workspace, so every selection remains visible, clickable, and keyboard
  reachable. Shared model/style choices remain selected while staff choose the
  remaining size or style; single-option products go directly to that choice,
  uneven option sets expose an explicit **Standard** choice, and duplicate
  variation descriptions require an exact SKU choice instead of silently using
  the first match.
- Changing an existing Order item's variation sends only the selected variant.
  Riverside retains the customer's original unit price, verifies both the
  saved variant and retained price in the Main Hub response, refreshes the
  original Transaction Record, and preserves before/after audit evidence.
- Overlay layering is now enforced across Register and Back Office. Drawers,
  nested drawers, modals, nested modal workflows, and system-priority overlays
  use explicit tiers and portal through the shared overlay root. Commission and
  combo editors, inventory mass assignment, Daily Financial Report preview,
  Customer history, and Customer Orders no longer depend on parent stacking
  contexts or DOM order to remain accessible.
- Focused contracts reject full-screen component overlays that are not portaled
  above shell chrome or that use shell-level z-indexes. Variation contracts
  cover model/size/style products, shoe-size-only products, uneven option
  depths, duplicate descriptions, exact-SKU resolution, and customer-price
  retention. Local Playwright E2E is intentionally skipped at operator
  direction; exact-commit GitHub Playwright remains a publication gate.
- Installing or refreshing the application rejoins an existing open Register
  session instead of asking staff to open a second drawer. Idle unlock and
  workstation reattachment preserve the opening float and original close
  record.
- Register idle security now always opens the dedicated **Register Locked**
  Access PIN screen. It never substitutes the Drawer Open workflow, and a
  successful unlock rejoins the existing drawer and retained sale context.
- The payment screen includes a current-sale **Restore** workspace beside
  terminal health. Staff can refresh provider health, re-verify and attach the
  exact approved Helcim sale or refund, reopen secure card entry, release an
  evidence-free blocker, select an available terminal, safely use another
  tender when permitted, rejoin the checkout, and retry **Record Sale** without
  leaving the sale for a separate operations queue.
- Daily Sales uses a dedicated receipt preview rather than the post-checkout
  Sale Complete screen. Shipping and alteration service activity appears in
  Daily Sales and Z-Report sources without being counted as merchandise sales.
- Register close now derives each check from the authoritative tender ledger,
  so the amount reviewed at close matches the Z-Report. Checks are included in
  each Register breakdown, and the financial Z-Report shows **Cash Deposit**,
  **Checks for Deposit**, and their combined **Total Deposit**. Operational
  recovery warnings remain in their audited workspaces instead of filling the
  financial report.
- A checkout that combines new merchandise with a payment on an existing Order
  appears once in Daily Sales and Z-Reports. The merchandise sale, public Order
  number, allocated payment, remaining Order balance, full tender, and total
  collected today remain visible without creating a second transaction card.
- Payment-only receipts contain no false **Taken Today** merchandise section.
  Mixed receipts separate **Payment on Order** from the new merchandise and
  reconcile **Total charged today** to the complete tender.
- A standalone RMS account collection remains an RMS payment receipt with its
  payment line. Only a payment carrying an actual existing-Order allocation is
  presented as **Payment on Order**.
- A fully paid takeaway checkout remains a sale receipt with its merchandise,
  tax, savings, and tender even though the resulting Transaction Record is
  fulfilled. Pickup/payment-history formatting requires explicit picked-up
  line evidence or payment-on-order work.
- Customer receipts reduce fee-only service lines to the service name and
  price: **SHIPPING FEE** or **ALTERATION FEE**. Internal SKU, variation, and
  service-workflow detail is not printed for those fee-only lines.
- Product search now distinguishes active searching, no matches, unavailable
  Main Hub results, and exact scanned-SKU failures without clearing a valid
  prior selection.
- Parent products use one grouped variation surface with large sequential
  choices, preserved selections, and complete price-range loading before an
  item can be added.
- The action carousel, keypad, salesperson selector, payment workspace,
  shipping shortcut, and service-line presentation remain usable at Register
  and tablet dimensions without hidden or partially actionable controls.
- Repeated low-value Register errors are deduplicated so staff see the
  operational problem without a toast storm obscuring the sale.
- Failed checkout recovery is reported once as an error toast and retained in
  the audited Register-close recovery workspace. It no longer creates a
  persistent top-bar or Cart warning that follows staff into later sales;
  genuine pending offline sync work remains visible.
- **Wedding Deposit** is now a dedicated Cart toolbar action. After staff select
  the paying customer, a guided workspace can open or start a party, link or
  create member Customers with roles, choose an exact held or existing-order
  destination for every beneficiary, and review the full allocation before
  Payment. The payer cannot be a beneficiary, each deposit remains a removable
  Cart row, and a deposit-only Cart can continue through normal Payment.
- A server preflight checks payer ownership, membership, destinations, live
  order balances, and salesperson before tender. Checkout repeats the checks
  under database locks. A decline creates no payer Transaction Record, member
  allocation, held deposit, booked activity, or receipt; reviewed allocations
  remain staged for retry while the declined provider attempt remains audit
  evidence rather than customer money.
- Wedding Deposit preflight now qualifies every selected member column in its
  joined party query. Valid party allocations proceed to Payment instead of
  failing with PostgreSQL's ambiguous-column error before CNP or another tender
  can begin. An exact database regression creates the payer, beneficiary,
  party, and member allocation and executes the real preflight query.
- Staff can choose **Collect & Build Orders** before party selection or
  **Deposit Only** when merchandise will be selected later. Collect & Build
  preserves any merchandise already in the payer's Cart, selects each funded
  member in sequence, and uses **Save Member Order & Next** to retain reviewed
  nonfinancial item drafts. Only after every member draft is ready does the
  workflow restore the payer's merchandise and expose one **Final Payment**.
- The salesperson responsible for payer merchandise is preserved separately
  from the salesperson responsible for the wedding-deposit workflow. Combined
  employee-price payer merchandise is supported in the same checkout, remains
  noncommissionable, and does not inherit the deposit salesperson.
- The approved payer checkout records merchandise only on the payer
  Transaction Record and records each party contribution separately. Register
  reporting shows the payer merchandise as booked sales and the wedding
  contribution in its dedicated fields without a duplicate activity or double
  counting. A decline posts neither side and retains the reviewed drafts.
- After approval, **Continue Wedding Orders** opens the payer-centered
  **Orders & Receipts** dashboard. **Choose Member & Add Items** reloads each
  reviewed draft on the correct member account and automatically attaches that
  member's exact source-tracked held deposit. Each member Transaction Record is
  still created only by its successful **Complete Sale / Record Sale**.
- Dashboard navigation and item selection never post financial work. Only a
  successful **Complete Sale / Record Sale** atomic checkout creates each
  member Transaction Record and redeems its exact source-tracked held deposit.
  A failed checkout rolls those writes back, and changing or clearing the
  Wedding member is blocked while Cart work exists so items and deposits cannot
  move to another Customer account.
- Sale Complete and every receipt format list each beneficiary, party, amount,
  and destination, separate member deposits from the payer's merchandise, and
  name the original payer on a member receipt. The Orders & Receipts dashboard
  provides payer/member receipt reprints after posting.
- Wedding deposit refunds are individual only. From the member Transaction
  Record, Riverside resolves the direct allocation or held-credit redemption
  to the exact original Helcim transaction without staff-entered provider IDs.
  Merchandise, tax, and reporting remain on the member Transaction Record, but
  the provider credit returns to the original payer's card. Both Customer
  histories and the refund receipt state that truth, and per-member capacity
  prevents one refund from consuming another member's share of the same charge.
- Sale Complete and every receipt format now distinguish the current checkout
  event from the lifetime payment history of a linked Transaction Record. A
  fully paid pickup shows **$0.00 collected at this pickup**, **Previously
  paid**, the remaining balance, and **No tender collected at this pickup**.
  Legacy `CARD` and `CREDIT_CARD` aliases display once as **Card**, and the
  internal Counterpoint unmapped sentinel is never shown as a customer tender.

## Returns, exchanges, and customer search

- Removing a paid, unfulfilled order item now preserves that item as refund
  evidence instead of deleting it. A replacement added to the same Transaction
  Record consumes the credit first: a lower-priced replacement leaves only the
  net refund, an equal replacement closes the credit, and a higher-priced
  replacement leaves only the added balance. Unrelated pickup items remain
  intact, and Register refund staging uses the preserved returned item.
- The externally completed `$67.04` card refund for Nathan Webster's removed
  shirt on `TXN-566201` is reconstructed through checksum-tracked migration 173
  as an itemized, non-restocking return and approved manual card credit. The
  remaining suit stays picked up, the Transaction Record remains fulfilled,
  and its total, paid amount, and balance reconcile to `$282.75`, `$282.75`, and
  `$0.00`. Fully returned lines now appear under **Returned Items** and no
  longer create open pickup, ready-notification, editing, or deletion work.
- The reviewed completed WALK-IN sale `TXN-624853` and its sole successful
  `$79.61` card payment are assigned to Glenn Jones (`GLENN-D8P9`) through
  checksum-tracked migration 172. Merchandise, tax, inventory, fulfillment,
  tender, and the `$0.00` balance remain unchanged, while Transaction activity
  and the customer timeline retain the reassignment evidence. Migration runners
  record this immutable, source-locked repair as not applicable on a database
  where the exact source Transaction does not exist; if that Transaction exists
  with evidence different from the reviewed sale, the repair still stops
  without changing it.
- Cancelling a paid order immediately loads its original merchandise as
  negative Register lines and opens the exact refund tender. A linked Helcim
  refund uses the server-owned original provider transaction, records the
  approved refund event, closes the internal recovery obligation, and leaves
  the cancelled Transaction Record at `$0.00` balance due.
- A staged paid cancellation, return, or exchange does not change the original
  Transaction Record, customer balance, inventory, loyalty, or audit history
  until the required refund is approved and **Record Sale** completes. Direct
  paid-record mutation routes fail closed so the payment screen remains the
  single settlement authority.
- A refund handoff from a Transaction Record now survives the required
  **Staff Access for this sale** screen. Riverside waits for the authorized sale
  operator before consuming the handoff, then loads the negative lines and
  opens **Pay** instead of leaving an empty cart.
- If ROS loses confirmation after an approved refund, **Restore** retries the
  same durable refund attempt and attaches the exact provider approval before
  committing the return or cancellation atomically. A manager may enter an
  externally verified refund reference only when the refund actually completed
  outside ROS; that path requires scoped Manager Access, masked-card evidence,
  a reason, and complete audit attribution.
- Refund-event reprints show the actual negative merchandise, original tax,
  exact refunded tender, masked Helcim card, and provider confirmation. Fully
  refunded Transaction Records cannot regain a false customer balance during
  later total recalculation; partial returns and exchanges retain only the
  legitimate unsettled remainder.
- Staged returns remain visible as the actual merchandise line with SKU,
  variation, negative value, and source Transaction Record.
- A reviewed return-value correction is retained on the specific returned line,
  cannot exceed the original paid value, and drives the same exchange or refund
  settlement amount while preserving original tax components.
- Customer lookup cancels stale requests and keeps exact customer selection
  stable across ambiguous scans and overlapping searches.
- Opening **Add Customer** closes the portaled Register search result panel so
  register actions cannot appear above or inside the customer intake drawer.
- Meilisearch is used only when its indexed document is at least as current as
  PostgreSQL authority; stale or unavailable search evidence falls back
  explicitly instead of being treated as current.
- The deterministic Playwright stack now disables Meilisearch and its daily
  reindex worker before startup, preventing its empty/fixture E2E database from
  replacing shared development or production indexes. GitHub Playwright lanes
  authorize Register cleanup only inside their disposable PostgreSQL service
  databases.

## Alterations intake and custody

- Register now separates **Quick Add**, which creates a tracked garment record,
  from **Fee Only**, which adds a non-taxable service charge without custody,
  due-date, pickup, or tailor-queue work.
- Full intake keeps garment choice, fitting decision, work requested, timing,
  capacity, fee, tag, and notes in one wide workspace with a pinned save action.
- Alteration services remain linked to the source merchandise or
  customer-owned garment and retain intake, status, work-item, and pickup audit
  history.
- Universal search can open the exact alteration directly into its planning and
  reassignment workspace.

## RMS Charge, Helcim, and reporting

- An already-approved historical Helcim payment recovered into ROS retains the
  processor approval date. The recovery action remains auditable without
  placing the historical tender on the recovery day's Daily Sales or Z-Report.
- Merchandise added to an existing open Transaction is booked on the date of
  the amendment without moving the Transaction's original business date.
  Daily Sales and booked Z-Reports net all same-day additions, removals, and
  price or quantity changes, include only a positive net increase as Booked
  Sales, and show signed Added, Change, and Removed detail. Zero-value swaps and
  net decreases remain audit-only. Initial booking lines show only regular and
  sale prices; the purple amendment amount appears only for a genuine later
  Added, Change, or Removed event, including same-day additions made through
  the existing-Transaction workflow.
- Daily Sales and Z-Reports present **Subtotal**, **Tax**, and **Total With
  Tax** separately across screen, print, text, and CSV output. Sales, Booked
  Sales, Net Sales, average sale, refund sales, and pickup sales are always
  pre-tax. Only **Total With Tax** and actual payment/transaction totals include
  collected tax.
- Order and customer timelines identify amended item names, SKUs, before/after
  prices, and signed value changes. Register and Order Workspace price edits
  re-read the saved line and report success only when the requested price
  persisted.
- The reviewed July 28 addition and price correction for Donald Dussing
  (`TXN-566034`, SKU `B-1417953`) is restored as a net $300.00 Booked sale plus
  its separately reported tax. Customer Interaction Timeline omits internal
  and reporting-excluded Counterpoint repair bookkeeping while the Transaction
  Record retains that audit evidence.
- Hosted Card Not Present approval automatically retries temporary ROS ledger
  confirmation failures while keeping the secure handoff open and explicitly
  warning staff not to rerun the card. Payments Health now presents terminal
  and hosted approvals together and can attach an exact unlinked CNP provider
  event to an existing open Transaction Record through the same audited
  Manager recovery flow.
- Current-sale Helcim recovery is actionable directly from the payment screen.
  An approved purchase attaches only when Register session, checkout, amount,
  currency, terminal attempt, and provider result match the current sale.
  Approved refund recovery uses the original durable attempt and idempotency
  key; amount-only or cross-sale evidence can never be attached.
- A pending Helcim attempt from an earlier checkout on the same Register no
  longer reserves the card reader against a new sale. ROS removes the prior
  checkout from terminal routing before dispatch while retaining its amount,
  identifiers, and provider evidence for Payments Health reconciliation. The
  current checkout remains protected against duplicate dispatch, and a truly
  simultaneous request on another Register can still reserve the shared reader.
- Selecting a non-default Helcim terminal from Restore requires real Manager
  Access with `payments.terminal.override`. The approval is scoped to the
  Register session, checkout, and selected terminal, revalidated by the server,
  and retained in the payment audit trail.
- Register customer results show current RMS Charge eligibility evidence, while
  actual balance and approval remain part of the RMS Charge workflow.
- Standard and 90 Day RMS plans use explicit approval numbers. A weekly account
  record with no open-to-buy requires audited Manager Access before the sale can
  be recorded.
- A simple take-now sale approved by Helcim can be recorded locally after Main
  Hub confirmation is lost, prints a pending-sync receipt, and replays the exact
  checkout idempotently after reconnection. Fulfillment-dependent workflows
  remain live-recovery only.
- RMS program tenders stay distinct from ordinary card activity in Register and
  Daily Sales reporting, while non-merchandise service activity is reported
  outside merchandise sales without changing tender truth.
- Payments Operations marks stale synchronization clearly so an older completed
  import cannot be mistaken for current processor evidence.
- Payment-only and combined checkouts preserve two distinct identities: the
  payment receipt Transaction Record created today and the older public
  Order/Transaction receiving the allocation. Daily Sales and Z-Reports show
  **Payment on Order** with both references, the applied amount, tender, and
  remaining balance. **Receipt** reprints the payment event; **Detail** opens the
  target order.
- Customer receipts use **Payments toward existing orders** and public
  Order/Transaction numbers. Internal allocation keys such as composite import
  identifiers are never printed, and a split allocation cannot repeat the same
  physical tender, cash-tendered amount, or change.
- Payment assignment labels prefer the public fulfillment Order number, then a
  customer-facing imported Order number such as `O-117888`, and use the ROS
  Transaction number only when no Order number exists. Internal Counterpoint
  composite references remain hidden.
- Sales by Hour now follows the same merchandise boundary as Daily Sales:
  alteration and shipping services remain visible and reconcile through tender
  and Z-close evidence, but do not increase merchandise sales, transaction
  count, active sales hours, or average sale.
- Historical Counterpoint reconciliation no longer creates current-day booked
  sales. The incident workflow suppresses booking-event triggers while restoring
  historical line truth, and the seven July 28 repair-generated events remain
  auditable while being excluded from Daily Sales. The correction changed no
  transaction, payment, tax, inventory, or customer-balance value.
